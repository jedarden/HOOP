# `claimed_at` Format Mismatch — Root Cause Analysis

**Date:** 2026-08-15
**Bead:** hoop-db972754
**Status:** Root cause identified, impact assessed

## Executive Summary

The `claimed_at` field in HOOP's collision index stores timestamps in **inconsistent RFC3339 formats** due to different code paths generating timestamps with varying precision and formatting. While all variants are valid RFC3339, the inconsistency creates parsing complexity and potential failure modes when timestamps are malformed or empty.

## Root Cause

### The Core Issue

The `sanitize_timestamp()` function in `supervisor.rs:1094-1112` **preserves original timestamp formats** when they pass RFC3339 validation, rather than normalizing to a canonical format. This design leads to multiple timestamp formats coexisting in the database:

```rust
fn sanitize_timestamp(ts: &str) -> String {
    if ts.is_empty() {
        return Utc::now().to_rfc3339();  // Fallback format
    }

    match DateTime::parse_from_rfc3339(ts) {
        Ok(_) => ts.to_string(),  // ❌ Preserves original format
        Err(e) => Utc::now().to_rfc3339()  // Fallback on error
    }
}
```

### Format Variants in Production

| Source | Format Example | Precision | Generation Location |
|--------|----------------|-----------|-------------------|
| Load test | `2026-08-15T17:09:14.900Z` | Milliseconds | `load_test.rs:151` |
| Production events | `2026-08-15T17:09:14.900167105+00:00` | Nanoseconds | `events.jsonl` |
| Fallback/sanitized | `2026-08-15T17:09:14.123456789+00:00` | Nanoseconds | `supervisor.rs:1098, 1109` |

### Why Different Formats Exist

1. **Load test code** (`load_test.rs:151`):
   ```rust
   ts: ts.to_rfc3339_opts(chrono::SecondsFormat::Millis, true)
   ```
   Uses `SecondsFormat::Millis` to reduce timestamp size in high-volume test data.

2. **Production events** from NEEDLE workers:
   Events written to `events.jsonl` contain full nanosecond precision timestamps generated by the standard `Utc::now().to_rfc3339()`.

3. **Fallback path** in `sanitize_timestamp()`:
   Uses standard `Utc::now().to_rfc3339()` when timestamps are empty or invalid.

## Impact Severity Assessment

### Severity: **MEDIUM**

**Why not HIGH:**
- All format variants are valid RFC3339
- `DateTime::parse_from_rfc3339()` handles all variants correctly
- Existing code has defensive parsing with fallback handling

**Why not LOW:**
- Format inconsistency creates maintenance burden
- Empty/malformed timestamps trigger error logging (performance noise)
- Test code produces different format than production (testing fidelity issue)
- Future code may assume a single format

### Specific Failure Modes

1. **Empty timestamp handling** (WARN logs, uses fallback):
   ```
   Empty timestamp in event, using current time as fallback
   ```

2. **Invalid timestamp format** (WARN logs, uses fallback):
   ```
   Invalid timestamp format '...' in event: premature end of input
   ```

3. **Cross-system compatibility** (potential issue):
   - External systems consuming collision index data may fail if they expect a specific format
   - Analytics tools may not handle multiple RFC3339 variants correctly

## Recommendations

### Immediate Actions (Low Risk)

1. **Document the format inconsistency**
   - Add inline documentation to `sanitize_timestamp()` explaining format preservation behavior
   - Update `CollisionIndexEntry` struct docs to note multiple valid formats

2. **Add format normalization tests**
   - Test that all three format variants round-trip correctly
   - Test parsing of each variant in all consuming code paths

### Medium-Term Improvements (Medium Risk)

3. **Normalize to canonical format in `sanitize_timestamp()`**
   ```rust
   fn sanitize_timestamp(ts: &str) -> String {
       if ts.is_empty() {
           return Utc::now().to_rfc3339_opts(SecondsFormat::Secs, true);
       }

       match DateTime::parse_from_rfc3339(ts) {
           Ok(dt) => dt.with_timezone(&Utc).to_rfc3339_opts(SecondsFormat::Secs, true),
           Err(e) => {
               warn!("Invalid timestamp format '{}': {}, using current time", ts, e);
               Utc::now().to_rfc3339_opts(SecondsFormat::Secs, true)
           }
       }
   }
   ```
   - **Pros:** Single format in database, easier debugging, better testing fidelity
   - **Cons:** Requires database migration to normalize existing data

4. **Change load test format to match production**
   - Modify `load_test.rs:151` to use standard `to_rfc3339()` format
   - **Pros:** Test data matches production format
   - **Cons:** Minimal impact, only affects test generation

### Long-Term Architecture (High Risk)

5. **Use strong typing for timestamps**
   - Change `claimed_at: String` to `claimed_at: DateTime<Utc>` in `CollisionIndexEntry`
   - Add custom serde serialization/deserialization
   - **Pros:** Compile-time guarantees, no format ambiguity
   - **Cons:** Breaking API change, requires migration planning

## Recommended Resolution Path

**Start with #1-2 (documentation + tests)** — low risk, high value
**Then implement #4 (test format fix)** — trivial, improves testing fidelity
**Consider #3 (normalization)** if format inconsistency causes operational issues
**Defer #5 (strong typing)** until major version bump or breaking change window

## Conclusion

The `claimed_at` format mismatch is a **design artifact** rather than a bug — all formats are valid RFC3339 and parse correctly. However, the inconsistency creates operational complexity and testing fidelity issues. The recommended path is to normalize timestamps at the `sanitize_timestamp()` layer, ensuring a single canonical format throughout the system while maintaining backward compatibility with existing data.
